# Config Studio — Antigravity & Gemini Project Rules 🚀

## 🗺️ Регламент ведения ROADMAP.md (Roadmap Clean-State Discipline)

**ОБЯЗАТЕЛЬНОЕ ПРАВИЛО ДЛЯ ВСЕХ СЕССИЙ:**
1. **Только незавершенные задачи наверху:** Секции текущего спринта и бэклога (`## 🎯 ТЕКУЩИЙ ЭТАП / В РАБОТЕ` и `## 🖧 ПЛАНИРУЕМЫЕ ПЛАГИНЫ`) должны содержать **строго невыполненные задачи (`- [ ]`)**.
2. **Всегда переносить выполненное под спойлер:** Как только этап, плагин, фича или пункт бэклога завершается, его **ВСЕГДА необходимо переносить вниз под спойлер `<details><summary>...</summary></details>` в раздел `## 📦 АРХИВ ВЫПОЛНЕННЫХ ЭТАПОВ (Released)`**.
3. **Верхний план никогда не захламляется:** Верхняя часть дорожной карты должна оставаться чистой, компактной и наглядной, отражая только актуальный фронт работ и предстоящие задачи.
4. **Обновлять сводную таблицу релизов:** При закрытии пакета задач добавлять новую строку с версией в сводную таблицу релизов внутри спойлера `✅ Сводный список выпущенных версий`.

## 🛠️ Главные регламенты разработки

1. **Сперва ядро (Core First):** Сначала механизмы ядра редактора, API и точек расширения.
2. **Предварительное обсуждение:** Перед реализацией каждой отдельной функции обязательно обсуждать её UX/UI, структуру данных и сценарии с пользователем.
3. **One Repo Per Plugin:** Каждый официальный плагин разрабатывается в отдельном GitHub-репозитории организации `config-studio`.
4. **Инженерная дисциплина (/ub-mode):** *First Make it Work* (Laziness Protocol, TDD, Idempotence), *Then Make it Right* (устранение первопричин, дробление, удаление мертвого кода), *Follow Practice* (Worktree Cleanup, Keep a Log, Commit often with proof).
5. **Обязательный релиз плагинов через GitHub Workflow (CI/CD Automated Releases):** Каждое расширение должно иметь рабочий процесс `.github/workflows/release.yml`. Релиз собирается, тестируется, упаковывается в `.cspkg` и публикуется в GitHub Releases автоматически по тегу версии (`v*`) или `workflow_dispatch`. Новые расширения создаются на базе шаблона `config-studio-plugin-template`.
6. **Обязательное использование библиотеки дизайна `@config-studio/ui` (Design System First):**
   * Все элементы пользовательского интерфейса (модальные окна `Modal`, кнопки `Button`, переключатели `Toggle`, карточки `Card`, бейджи `Badge`, поля ввода `Input`/`Textarea`, выпадающие списки `Select`/`Dropdown`, вкладки `Tabs` и области прокрутки `ScrollArea`) ДОЛЖНЫ строиться исключительно на базе библиотеки `@config-studio/ui` (каталог `web/src/components/ui`).
   * **Категорически запрещено** создавать самописные `div` со скроллбарами (`overflow-x-auto`, `overflow-y-auto`) или дублировать стандартные контролы в обход дизайн-системы.
   * Для любых горизонтальных и вертикальных областей прокрутки **ОБЯЗАТЕЛЬНО** используется компонент `<ScrollArea orientation="horizontal" | "vertical" | "both">`, в котором по умолчанию активирована нативная плавная прокрутка колесиком мыши (`horizontalWheel`) без паразитного скролла родительских контейнеров и страниц.

## 🛡️ Безопасность кодовой базы и предотвращение регрессий

Эти два инструмента решают две главные проблемы при работе AI-агентов с существующими проектами:
1. **`doubled-graph`** защищает проект на уровне **архитектуры и связей** (предотвращает скрытые поломки и регрессии в других частях системы).
2. **`ub-mode`** управляет агентом на уровне **инженерной дисциплины** (заставляет писать тесты, делать минимальные точечные правки и не плодить костыли).

### 1. Инструменты `doubled-graph`

| Инструмент | Что делает | Когда применять |
| :--- | :--- | :--- |
| **`impact`** | Анализирует «зону поражения» (*blast radius*). Показывает список вызывающих функций вверх и вниз по цепочке вызовов и оценивает риск (`LOW`, `HIGH`, `CRITICAL`). | **До** внесения любых правок в существующий метод/класс. |
| **`context`** | Собирает 360° срез по символу: контракт, вызывающие и вызываемые модули без необходимости скармливать агенту гигантские файлы целиком. | Перед проектированием доработок или сложным рефакторингом. |
| **`detect_changes`** | Проверяет подготовленные к коммиту файлы (`git diff --staged`) на расхождения с архитектурой и контрактами. | **Перед** коммитом в git. |
| **`analyze`** | Сканирует файлы и актуализирует базу графа. | При первом запуске и после подтягивания чужих изменений из git. |

### 2. Принципы `ub-mode`
- **TDD (Test-Driven Development)**: сначала пишется падающий тест, подтверждающий проблему/задачу, затем минимальный код.
- **Laziness Protocol (Минимальный диф)**: не трогать соседний код, не переформатировать полфайла, решать одну задачу за раз.
- **Fix Root Causes**: устранять первопричины сбоев, не глушить ошибки условиями.
- **Pinning & Refactoring**: перед рефакторингом легаси фиксировать поведение тестами (*pinned behavior*).
- **Атомарные коммиты**: каждый шаг проверяем и подтвержден тестами.

### 3. Обязательные чекпоинты агента
1. Перед изменением или удалением любой функции/метода ОБЯЗАТЕЛЬНО вызвать MCP-инструмент `impact` для оценки blast radius.
2. Если риск `HIGH` или `CRITICAL` — описать пользователю затронутые зависимости и согласовать стратегию.
3. Перед созданием коммита вызвать MCP-инструмент `detect_changes(scope="staged")`.
